## 네임스페이스와 모듈

☞ 자바스크립트는 전역 공간이 하나이기 때문에, 변수나 함수 이름이 충돌할 수 있음.
이를 방지하기 위해 네임스페이스와 모듈을 사용함.

- 네임스페이스
  : 관련된 변수나 함수들을 하나의 객체로 묶어 이름 충돌을 방지하는 방법
  ☞ 객체 리터럴을 사용하여 네임스페이스 생성


☞ 'namespace'란 키워드 뒤에 오는 이름으로 공간을 만든 것
☞ 네임스페이스 내부에 정의된 변수나 함수는 외부에서 접근할 수 없으며, 네임스페이스 이름을 통해 접근해야 함.
☞ 'export' 키워드를 제거하면 외부에서 접근 불가.(캡슐화)
☞ 한 네임스페이스가 다른 네임스페이스 포함 가능.


☞ 네임스페이스는 코드의 구조화와 충돌 방지에 유용하지만, 대규모 애플리케이션에서는 '모듈 시스템'이 더 선호됨.

- 모듈
  : 파일 단위로 코드를 분리하여 네임스페이스를 제공하는 방법
  ☞ 각 파일은 자체적인 스코프를 가지며, 필요한 변수나 함수를 'export' 키워드를 사용해 외부에 공개하고, 'import' 키워드를 사용해 다른 파일에서 가져올 수 있음.
  ☞ ES6 모듈 시스템 사용


☞ 모듈은 네임스페이스보다 더 강력한 캡슐화와 코드 재사용성을 제공함.
☞ 모듈 시스템은 의존성 관리와 트리 쉐이킹(tree shaking)과 같은 최적화 기법을 지원함.
☞ 모듈은 파일 단위로 관리되므로, 프로젝트 구조를 명확하게 유지할 수 있음.
☞ type도 모듈로 export 해서 index.ts 내 타입 가드할 수 있음.


☞ 'T'로 주어진 객체의 속성들 중 값의 타입이 'U'인 속성들만 골라내는 유틸리티 타입
☞ import된 유틸리티 타입에 문자열과 함께 제네릭으로 전달하면, 속성들 중 값의 타입이 boolean인 속성들만 골라내 AdminProps 타입이 생성됨.
☞ 네임스페이스와 모듈은 자바스크립트에서 코드의 구조화와 충돌 방지를 위한 중요한 개념이며, 각각의 장단점이 있음.

---

### 네임스페이스 vs 모듈 정리

| 구분        | namespace               | module             |
| ----------- | ----------------------- | ------------------ |
| 스코프      | 하나의 전역 스코프 내부 | 파일 단위 스코프   |
| 사용 방식   | `namespace` 키워드      | `import / export`  |
| 캡슐화      | 제한적                  | 강력               |
| 확장성      | 소규모 프로젝트         | 중·대규모 프로젝트 |
| 현대적 사용 | ❌ (레거시 위주)        | ✅ (권장 방식)     |

☞ **TypeScript 공식 권장 방식은 ES Module(import/export)**  
☞ namespace는 기존 JS 코드 또는 단일 파일 구조에서만 제한적으로 사용

---

### 언제 네임스페이스를 쓰면 좋을까?

- 단일 파일 스크립트
- 외부 번들러 없이 사용하는 환경
- 레거시 TypeScript 코드 유지보수

---

### 언제 모듈을 써야 할까?

- 실제 서비스 / 팀 프로젝트
- 기능 단위로 파일 분리
- 트리 쉐이킹, 의존성 관리가 필요한 경우

---

### 실무에서의 권장 패턴

- **타입, 인터페이스, 유틸리티 타입 → 별도 파일로 분리**
- **도메인 단위로 모듈 구성**
  - `user.ts`
  - `auth.ts`
  - `utils.ts`
- `index.ts`에서 조합 및 실행

☞ 네임스페이스는 “개념 이해용”
☞ 모듈은 “실전 필수”
